# Stack Build — Stage 2: training evidence

## Delivered

The read-only evidence engine derives pieces, progression, historical records, current and sealed weeks, volume, and weekly comparisons from existing workout sessions. The adapter feeds that result into Stage 1's renderer. No schema, workout completion, or persistence behavior changed.

The sandbox now has an **Evidence** tab with **Saved workouts**, **Example history**, and **Inspect evidence**. The inspector shows the earlier session, matched regular-set positions, before/after performance, and the earlier personal best behind each reward. The example sessions are in memory only; their fixed reference date is 23 September 2026. Saved history uses the device's local calendar and refreshes on foregrounding, selection, and once a minute while the evidence view is visible.

Start the sandbox using the commands in `stack-build-stage-1.md`. If a cold launch opens Home before the deep link is handled, run `xcrun simctl openurl booted stackbuild://build-sandbox` after the app loads. Settings also has the development entry point.

## Interfaces

- `deriveBuildState(sessions, now, rules?)` in `features/build/evidence.ts`: pure, deterministic projection; the caller supplies the clock. Returns ordered pieces, active historical weeks, an always-present current week, total metrics, and date diagnostics.
- `adaptBuildHistory(sessions, now, rules?)` in `features/build/adapter.ts`: returns both evidence state and renderer-ready slabs.
- `buildStateToSlabs(state)`: one composite for each historical active week, and one slab per current-week piece. The source pieces remain intact for future Case reconstruction.
- Shared calendar helpers moved to `store/workoutCalendar.ts`. Existing imports from `workoutStore` remain compatible through re-exports. Records now uses the pure calendar module, making its existing best-set comparator reusable without loading the native store or SQLite.

## Rules made explicit

- Completed, non-retroactive sessions create pieces. A completed session with no performed sets still creates a baseline piece with zero metrics. Incomplete sessions and retroactive attendance create nothing.
- Exercise identity follows the existing exact logged name. Progression additionally requires the same load type. This is bounded by the current schema: historical exercise names/load types are not immutable snapshots.
- Compare regular sets by their ordinal position, retaining skipped/unperformed slots. Bonus sets do not count toward thickness. A newly added set without a prior match does not count either.
- Compare against the latest earlier session containing usable regular sets for that exercise/load type. A skipped-only or bonus-only appearance does not erase that baseline. Duplicate exercise entries concatenate their regular slots in logged order; each exercise name counts once toward the bucket.
- More load with at least the same reps, or more reps at the same load, improves a set. Bodyweight progression compares reps. One improved matched set makes that exercise improved; other regressed sets do not cancel it under the agreed exercise-count rule.
- Zero/one/two/three-or-more improved exercises select 1.00×/1.15×/1.30×/1.45×. Eligible-exercise counts and every improved set remain inspectable.
- Gold uses the existing load-first, then reps PR ranking across all earlier verified performed sets, including bonus sets. Merely labeling a set `pr` does not award gold. Each exercise can earn one record per session. The first session establishes a baseline even if later sets within it outperform earlier ones.
- More load with fewer reps can therefore earn gold without adding thickness. This intentionally keeps the existing Records definition separate from comparable-performance progression.
- Volume uses completed, non-skipped set load × reps in canonical kilograms; display respects kg/lbs. Non-finite/negative loads and non-positive reps do not supply performance evidence. Canonical bodyweight logs have zero load.
- History is sorted by timestamp, then numeric-aware session ID for ties. Identical duplicate session IDs are deduplicated; conflicting duplicates throw instead of choosing an arbitrary source record.
- Monday starts a local training week. Historical active weeks are sealed immediately in derived state, without animation or persisted seal records. Empty weeks have no geometry. Weekly volume comparisons use the previous active week, skipping gaps.
- Date-only values preserve the app's local interpretation. Invalid dates and future-week records are excluded with diagnostics; source records are not changed. Time-zone travel can regroup timestamped history under the current app convention.
- Tunable weekly compression and min/max bounds affect geometry only. Empty current weeks have zero composite height. No historical animation queue is generated by this layer.

## Boundary and next stage

This is the Stage 2 inspection harness, not the final Monolith or Case UI. Stage 3 adds the composed Monolith screens, week selection, and current-week detail. Workout reward navigation and fusion presentation remain later stages.

Physical-iPhone visual/performance acceptance from Stage 1 is still pending. The user explicitly requested proceeding to this independent data stage while that checkpoint remains open.

## Visual tuning checkpoint

Full Strata is now the initial and reset lamination, with key corner 0.24 and weekly compression 0.35. Build rendering preserves the existing category hues while increasing saturation, brightness, and side-face illumination. Gold is brighter yellow and remains independent of workout pigment.

Each PR workout gets a thin seam at the upper edge of its own stratum (at most 10% of that stratum's height). Key-corner faces retain all workout colors. Only a PR in the top workout can add a thin gold top perimeter; a lower workout's PR never highlights the entire block. Multiple PR workouts produce separate seams; no PRs produce no gold.
