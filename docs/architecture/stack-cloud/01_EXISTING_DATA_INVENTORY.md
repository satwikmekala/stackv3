# Existing persistence, authoritative data, and upgrade risks

Investigated 8 October 2026 against the working tree. This is a source audit, not an inspection of a user's device or deployed database. Evidence references use repository-relative `path:line` locations. Unrelated existing UI modifications were left untouched. The inventory includes current code and the actual upgrade dispatcher; historical versions not represented by checked-in fixtures are explicitly not assumed equivalent to fresh installations.

## Storage map and current capabilities

The primary database is Expo SQLite `workouts.db`, schema version **24** (`store/workoutDatabase.ts:48`). The app has one local profile (`id = 1`) and integer row identities. It does not have a Stack account owner column, durable installation namespace, global record IDs, record revisions, tombstones, cloud cursor, or transactional sync outbox in this schema. Hevy's `account_id` is import provenance, not a Stack account.

A complete JSON export/replace restore already exists. `store/workoutBackup.ts:5` enumerates 18 backed-up tables including `sqlite_sequence`; the recovery-receipt table is intentionally omitted. `features/settings/data.ts:20` adds four AsyncStorage preferences. Export and restore require no active workout (`features/settings/data.ts:24`). This is user-directed local file backup, not automatic cloud protection or synchronization. Files are written to app cache and handed to the share sheet (`features/settings/data.ts:63`). CSV is a lossy human-readable history export, not a restore format (`store/workoutBackup.ts:146`).

The server has a separate SQLite `routine_shares` store on a configured Railway persistent-volume path (`server/src/routineShareStore.mjs:11`), not a PostgreSQL workout/account store. Shared routines are public capability-link snapshots and must not be treated as a user's private cloud history.

## Historical migrations: actual upgrade behavior

There is no numbered immutable migration directory. Schema DDL, shape detection, backfills and version gates coexist in `store/workoutDatabase.ts`. Startup executes current `CREATE ... IF NOT EXISTS` DDL **before** reading `PRAGMA user_version` (`:1803`), then adds load/state/measurement fields before branching. A schema version does not uniquely identify shape: receipts and `is_stack_plan` were added without requiring a version bump (`store/workoutBackup.ts:30`, `store/workoutDatabase.ts:438`, `:1454`).

No general future-version rejection or whole-database pre/post integrity gate appears in this initializer. Do not open a future cloud snapshot directly with it. Production cloud adoption should take a recoverable consistent pre-migration snapshot, verify expected schema shape and foreign keys, reject unknown newer versions, then migrate copies before replacing the live dataset. Migration failure must leave the only authoritative copy intact and workout data accessible through recovery tooling.

Checked-in real SQL fixtures cover v14, v15, v16 and v17 (`tests/fixtures/workout-v14.sql` and siblings); later tests construct older shapes from harnesses. Actual release-era fixtures for pre-v14 and every same-version shape must be collected before claiming universal upgrade support. Current tests contain version-specific expectations from earlier schema baselines; their existence alone is not a statement that the entire current suite passes.

## Authoritative reconstruction and identity semantics

The minimum lossless reconstruction set is: session rows and ordered workout types; every session-exercise and set (including target, skipped, bonus and source fields); referenced exercise definitions; notes; all custom splits/workouts/exercise occurrences including hidden Stack plans; profile; and **all import provenance and JSON facts**. Keep the current local template tables in initial exact snapshots until a versioned catalog+override representation has proven equivalent. Preserve the four backed-up preferences for user-visible continuity. Drafts are separate unfinished user work, with an explicit product policy rather than silently folded into workout history.

Imported JSON contains facts that are absent from normal SQL rows: source kinds (including warmups), notes, rest, supersets, distance, RPE, timestamps and unsupported metrics (`features/import/models.ts:5`). Session hydration joins `imported_workouts`, parses JSON and reconstructs per-set source kind (`store/workoutDatabase.ts:862`, `:927`); PR reads exclude warmups using that source kind (`:2055`). Routine launch reads imported targets (`:3139`). Excluding these tables loses information and changes calculations, even if all `sets` survive. CSV-import identities are content fingerprints and occurrence ordinals; they are not Stack users (`features/import/hevyCsv/parser.ts:16`, `:124`, `:173`).

Build is a pure read-only projection (`features/build/evidence.ts:83`). It derives pieces/weeks/metrics from verified native history, excludes incomplete and retroactive sessions, and also excludes imported workouts (`store/verifiedSessions.ts:4`). Records, progression, volumes, charts, overdue selection, rotation and training queues should be recomputed from restored facts and a pinned algorithm version. Earned Build data is not the AsyncStorage casting/fusion ceremony state. A change in source flags, exercise name, set order, tie-break identity or calendar interpretation can change derived results.

Weights and target weights are kg-canonical; display/input units are separate (`store/weightUnits.ts:3`). Preserve floating-point values losslessly through JSON/SQL; no kg↔lb round-trip on restore. The conversion factor is 2.20462 and user kg/lb increments are independent (`store/weightUnits.ts:7`, `:27`). Seconds are integer duration fields; never reclassify old reps using today's catalog. Preserve nullable `completed_at`; `date` can be timestamp or a local calendar date, parsed differently (`store/workoutCalendar.ts:9`). Current week grouping uses the device local calendar. Future cross-device deterministic calendars require an explicit timezone/date policy while preserving original strings; guessing a timezone for old date-only records is data invention.

Integer IDs are scoped to one database. Preserve them during exact restore or maintain complete mappings for FKs, routine provenance, focus, imports and draft references. New globally unique IDs must be added transactionally without rewriting these integers as a first step. Session IDs stringified in JS and numeric-aware tie breakers influence ordering (`features/build/evidence.ts:108`); swapping to UUID lexical ordering can change same-time PR/Build attribution. Retain deterministic historical ordering metadata.

Exercises are joined by ID but history/records/progression also use exact names. Renaming or deleting an exercise with completed-set history is blocked (`store/workoutDatabase.ts:3711`, `:3756`); a cloud merge must not circumvent that guard by deduplicating matching names. Session measurement is snapshotted but exercise display names come from the catalog join, so reference integrity and naming semantics remain important. Custom routine source IDs in sessions intentionally survive deletion without FK enforcement (`:492`). Do not turn those into mandatory cloud FKs to live routines.

## Backup implementation strengths and concrete gaps

Current capture reads all whitelisted tables in one synchronous transaction (`store/workoutBackup.ts:20`). Restore validates structure before deletion, uses a transaction with deferred foreign keys, clears recovery receipts, replaces rows in dependency order, restores sequence counters, then checks foreign keys and SQLite integrity (`:115`). Compatibility adapters accept schema 21–24 at current v24 and patch known additions; they do not implement arbitrary historic/future restores (`:34`). Completed-only guard rejects active sessions (`:85`). This is a useful starting point for a private snapshot serializer, not a network replication contract.

SQLite and AsyncStorage changes cannot share a transaction. The existing settings restore attempts compensating restore on failure (`features/settings/data.ts:119`), but process termination between commits or failure of compensation can leave mixed state. Cloud restore needs staged verification and an atomic dataset switch/journal with recovery on next launch. Existing export reads preferences separately from SQL; synchronizing all domains needs either a captured manifest with explicit per-domain revision or moving backup-worthy preferences into SQLite.

Current manual backups are unencrypted JSON and require the user to save/share the file. The 50 MiB picker ceiling (`features/settings/data.ts:97`) is a local import limit, not a validated capacity promise for years of history. No cloud checksum, authenticated manifest, retention, ownership binding, remote acknowledgment, recovery-point age, background scheduler or restoration drill is implemented by these helpers.

The one-in-progress-session partial unique index (`store/workoutDatabase.ts:569`) is local. Future multi-device sync must not download a second active session into that constraint or silently discard one. Session completion has a performed-set guard (`:401`, `:3604`), but the trigger only protects 0→1 updates, not every possible inserted/restored completed row. Restore semantic validation must distinguish legitimate retroactive/imported history from malformed native completed sessions rather than relying on SQL alone.

Existing destructive reset and active discard paths are local deletes (`store/workoutDatabase.ts:2910`, `:3995`), not tombstones. Future synchronization must instrument these and every edit atomically with an outbox; diffing current tables cannot reliably reconstruct deletions. Reset/restore currently do not clear every presentation key (casting/fusion); account/dataset namespaces and runtime invalidation should prevent key reuse. Pending native commands must be invalidated on restore/account switch before the new active dataset is exposed.
