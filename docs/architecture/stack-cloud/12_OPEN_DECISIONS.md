# Decisions for founder approval

Status: proposed defaults, 8 October 2026. Approval authorizes a future implementation scope; this documentation pass changes no application behavior or production resources. Assign named people to the role owners below before implementation. Record approve / reject / requested change and decision date in this file or the team's decision tracker; silence is not approval.

RPO means the amount of recent data potentially lost in a disaster; RTO means time to recover the service. Neither measures how recently the user pressed **Back up now**. For manual launch, unbacked changes since that action can be arbitrarily old and remain outside the recovery promise.

## Data and product policy decisions

| ID / decision | Proposed default to approve | Consequence / gate | Accountable role |
|---|---|---|---|
| D07 — Backup inclusion | Completed workouts, required exercise/catalog/template data, imported evidence, saved routines/notes, profile and portable preferences. Exclude active sessions, unsaved drafts, device permissions and transient/native state. | The UI must name exclusions. Current active workout cannot be recovered on another phone; changing that needs active-session ownership design. | Product + data lead |
| D08 — User checkpoint retention | At most **3 completed checkpoints**: latest plus up to two previous checkpoints captured within **30 days**. Keep the latest indefinitely until explicit user/account deletion even when it is older than 30 days. Restore pins temporarily defer normal pruning. | “Indefinitely” means no automatic inactivity expiry under this policy; service shutdown requires an announced export window. More history increases storage and personal-data retention. Expose older snapshots only when actually present. | Founder + privacy/operations owner |
| D09 — Temporary retention | Incomplete upload chunks expire after 7 days; restore pin expires after 24h and can renew; local rollback copy retained 7 days or until explicitly removed; independent operator copies expire within 30 days. | These have different purposes and must not be conflated. Document storage use; failed upload never evicts the latest verified checkpoint. Confirm provider settings meet maximum operator retention. | Operations + mobile lead |
| D10 — Deletion | Disable account cloud access immediately on accepted deletion; live account/data purge target ≤7 days; operator copies age out ≤30 days. Separate durable deletion ledger prevents resurrection. Native Apple token revocation is required. | Targets cannot appear in final privacy copy until provider/legal validation. Scope “remove from this iPhone”, “delete cloud data”, and “delete account” separately. Future normalized cloud state is included in cloud deletion. | Founder + privacy/security lead |
| D11 — Local history on sign-out/deletion | Sign-out retains local history with its existing owner and pauses upload. Account deletion offers an explicit choice to keep a local-only copy; never silently re-upload it after recreating an account. | Switching accounts needs isolated datasets; no relabeling A's history as B's. Decide final keep-local checkbox default during UX review; default destructive action must explain actual local consequence. | Product + security lead |
| D12 — Account prompt | Keep guest onboarding unchanged. Offer one dismissible prompt after a first completed workout; existing users get it after their next completed workout. Settings remains the permanent entry. | Settings-only introduction is a lower-friction alternative. No recurring workout interruptions; measure adoption without tracking workout contents. | Founder + product lead |
| D13 — Second device | Permit restore after sign-in; explicit takeover required to enable writing backup from replacement device. Old device can log offline but its stale writer fence cannot publish. | No simultaneous-device convenience promise. Warn that unsent old-device data has not moved. | Product + sync lead |
| D14 — Conflicting histories | First release lets users preserve/export local history, restore a verified cloud snapshot with a rollback checkpoint, or cancel. Keeping a conflicting local dataset leaves cloud association paused. | No account merge or cloud replacement feature hidden behind sign-in. User-assisted merge tooling is a separate future scope. | Founder + product/data leads |
| D15 — Semantic compatibility | Preserve original IDs, canonical kilogram values, session ordering and imported evidence; fix time/timezone/rule version in round-trip verification. | Cross-timezone Build/week display parity is not currently promised. Founder must choose a timezone/product rule before future multi-device derived-view equality is promised. | Product + data lead |

Deleting an individual workout cannot retroactively edit immutable retained snapshots. Document that earlier snapshots may contain it until expiry; full cloud/account deletion takes the separate purge path. The most recent checkpoint's indefinite retention is not a promise to preserve deleted data indefinitely after an explicit purge request.

## Decisions intentionally deferred

- Google rollout and other providers until explicit linking is safe; architecture supports them without rekeying workouts.
- Bidirectional multi-device writes, active-session handoff and fine-grained conflict merges.
- Private friends/coach access: explicit grants, expiration, audit and revocation required; never public-share-token authorization.
- Web dashboards/cross-platform clients and subscription entitlements; keep these separate from ownership and provider subject.
- E2EE, social feeds, large-data partitioning and object storage until product need or measurements justify them.
- Account/history merging, replacing cloud history with an unrelated local dataset, and provider-loss support recovery beyond proven identity control.

Deferral is not an exemption from today's portability, owner-scoped constraints or recovery contracts. No deferred feature should be implied by launch copy.

## Suggested review order

Approve D01–D06 first so engineering has a coherent provider, scope and recovery budget. Resolve D07–D18 before privacy and UX copy is frozen. Assign D19–D22 owners before TestFlight. For each rejected default, update its dependent documents and release gates before implementation begins; do not let different implementation worktrees choose contradictory policies.
